## 1. What V3.1 is, and is not

V3.1 is **not a new platform**. It is the integration and consolidation of the MYTHOS
ecosystem as it exists on 2026-09-24: one director, one default local executor, two Claude
escalation tiers, one memory layer, one record of change — all through components that were
already merged. The rule is the repository's own: **SEARCH → REUSE → ADAPT → CONNECT → BUILD
LAST.**

V3.1 was undefined in writing before this document (measured 2026-09-23: `grep -rl "V3.1"`
over the tree returned nothing; the only V3 scope was the boundary list in the V2 master plan
§21). This document is that definition, written **after** the audit in §3 and not before.

## 4. What the director decides, and how it was decided here

TASK → PLAN → RESEARCH → REUSE → MODEL → EXECUTION → VALIDATION → REPAIR → ESCALATION →
REVIEW → RECORD → COMPLETE. The model choice per V3.1 work item, with the reason:

| Work item | Model | Why |
|---|---|---|
| audit, capability map, this document | FABLE | needs the whole repository and the estate in view; 8,192-token Qwen cannot |
| `haddad-agent.js` escalation tier + report turn | FABLE | a 1,254-line provider; a whole-file `write_file` cannot fit 1,536 tokens per turn — Qwen cannot edit files of this size, measured, not assumed |
| registry tracks, seed file | FABLE (content), Qwen (validation) | content needs evidence from 15 projects; validation is a file test |
| researcher / tester / small-file implement tasks | **Qwen** via real Issues (#426, #427, …) | the bounded, testable work the runner is built for |
| diagnosis when Qwen fails a repair | Sonnet, then Opus by §5.3 | the escalation chain itself |

Honest limit, recorded so it is not re-learned: with an 8,192-token window, 1,536 tokens per
turn and whole-file writes, Qwen's unit of work is **a file under ~4 KB with a file-based
acceptance check**. That is why "maximum real execution by Qwen" in V3.1 means many small
verified tasks, not the large edits above.

## 5. Changes made in V3.1 (branch `mythos-haddad/v3.1`)

### 5.1 Nothing new is built

No queue, scheduler, executor, provider, registry, router, memory store, event system,
monitoring stack, MCP server, agent framework or runtime was added. Every change below is a
CONNECT or an ADAPT of a file that already existed, plus one seed and two test files.

### 5.2 Qwen structured output (reliability, §15 of the brief)

- `free-llm/adapter.js`: forwards `opts.responseFormat` as `response_format` — only when a
  caller asks; every existing request is byte-identical.
- `providers/haddad-agent.js`: when the model's final message carries no readable report, ONE
  constrained turn (no tools, `response_format: json_schema` strict — `mythos_report: const
  true`, status enum, arrays, nullable commit) asks for the report only. The answer is appended
  as the fenced block and handed to the **same** parser (`lib/report.js`) and validator
  (`lib/work-validation.js`) as before. Bounded: one per execution, never when the turn budget
  is spent, off with `opts.structuredReport === false`. The constraint narrows what the model
  can emit; it vouches for nothing — a constrained answer that is not a report is still the
  same named rejection.
- Measured on the live runtime before writing a line: the full schema is honoured (85
  completion tokens, parseable, `mythos_report: true`).

### 5.3 Sonnet → Opus escalation (§6, §7, §18 of the brief)

- **Tier by the task's own signals, no new table.** `escalationTier(task)` calls
  `lib/model-policy.js selectModel()` — the same explicit-wins / scored haiku·sonnet·opus policy
  the VPS executor already uses — and maps `opus` → **deep**, everything else → **standard**.
  A task that names `Model: opus` is deep; a task whose instruction carries the policy's
  architecture/security/complexity terms scores deep; a typo fix is standard.
- **Standard tier** = `HADDAD_AGENT_DIAGNOSER` (Sonnet), unchanged: diagnosis on the last
  repair round, no tools, Qwen executes.
- **Deep tier** = `HADDAD_AGENT_DIAGNOSER_DEEP` (Opus). Reached two ways: (a) a deep-scored task
  gets Opus on its last standard round; (b) a standard task whose Sonnet-diagnosed round still
  fails validation gets **one** extra round (`MAX_DEEP_ROUNDS = 1`) with Opus. Opus is asked at
  most once per task either way; without a deep diagnoser configured the loop is exactly the
  three-execution loop it was.
- Every decision is in the tool trace (`escalation: tier requested X, used Y (reason)`), so
  "why did Opus get asked?" is answerable from the task record.

## 6. Operational truths carried forward (do not re-learn)

- **MERGED ≠ RUNNING.** The worker loads its modules once; after a fast-forward it *reports*
  the new head and *runs* the old code. Compare `ExecMainStartTimestamp` with the merge time and
  read `/health → code_identity` (measured at start). V3.1's provider changes are live only
  after `systemctl --user restart mythos-haddad-worker.service`, done at an idle queue.
- The health WARN on `ai_runtime` is the frozen-cache false alarm fixed by open PR #407.
- Under >3 concurrent Claude sessions the 7.2 GiB box exhausts memory and hangs SSH; check
  `free -m` and the session count before blaming a subsystem.
- A tool-layer refusal is not a boundary when the tool can run code; the sandbox is.
