## 1. The finding that scopes V3.2

The working title was "AI system intelligence", with ten candidate capability areas. The audit
(§3) found that **every one of them already has a component in the repository** — a project
registry, an OTHKM graph, a reputation store, a roadmap selector, a dependency-waiting queue,
an event stream on the console. What is missing is not intelligence machinery. It is that
**four of those components are disconnected from the live path, stale, or unable to hold the
data they were built for**:

| Component | Built for | What the audit measured |
|---|---|---|
| `core/reputation.js` | learn which agent succeeds at which capability | the router **consults** it, but on the live Haddad path **nothing records an outcome** — only the core orchestrator (off) and the free-LLM pool write to it |
| `projects/oth-knowledge/lib/graph.js` | project/entity relationship graph | OTHKM has a `relationship` kind and `extract.addRelationship()`, but **the seed loader cannot load relationships** — V3.1 had to express "A uses B" as prose claims the graph cannot walk |
| `core/roadmap.js` | pick the next highest-value safe capability | its recorded state is **stale**: it recommends "Dependency DAG" first, and lists Agent Registry, Tool Registry, MCP Tool Layer, Validator, Worktrees, Reputation and Knowledge Graph as planned or conceptual — all exist in code with tests |
| `scripts/project-intelligence.js` | validate the project registries | **fails its own validation** (6 errors: six skills added 2026-08-26 were never registered), which is also the whole cause of the governance suite's long-standing "baseline" 33/3 |

So V3.2 is **ecosystem intelligence by connection**: make the existing components hold true
data, feed them from the live path, and give the director one read-only question it can ask
before building anything — *"do we already have this?"*

## 4. Specification

### 4.1 OTHKM relationships in seeds (candidate 3)

- `projects/oth-knowledge/lib/seed.js` accepts `relationships: [{ from, to, rel_type, metadata? }]`
  where `from`/`to` are seed keys of already-loaded records; it calls the existing
  `extract.addRelationship()`. Unknown key → `OTHK_SEED_INPUT`; the secret gate already covers
  the whole seed. Idempotent like every seed record.
- `rel_type` vocabulary for the ecosystem: `uses`, `depends_on`, `reuses`, `can_execute`,
  `federates`, `serves`, `observes`. Free strings are accepted by the model (it is data, not a
  schema), the vocabulary is pinned in the test.
- The ecosystem seed gains typed relationships mirroring its relationship claims and the
  registry dependencies; `graph.neighbors()` then answers "what does X use / what uses X".

### 4.2 Project intelligence and the reuse query (candidates 1, 4)

`scripts/project-intelligence.js` (existing, dependency-free, read-only) is repaired and gains:

- `reuse "<need>"` — scores the need's words against: portfolio tracks (name, notes,
  `shared_platform_capabilities`), the agent-skills registry (`purpose`) and `.claude/skills`
  descriptions, the executor's agents/roles/skills/tools/MCP capability configs, and the
  committed OTHKM seeds (claims, entities, relationships). Prints JSON
  `{ kind: "data", query, matches: [{ source, id, file, score, text }] }`. **Output is labelled
  data**: it cites files and never contains an instruction the caller is meant to follow.
- `project <id>` — one project's identity, dependencies, dependents (reverse deps), reusable
  capabilities and its seed relationships (both directions).
- `outcomes [--store <dir>]` — read-only summary of an executor task store by provider × role:
  n, completed, failed, blocked, mean repair rounds, diagnosis rate, context-exhaustion count.
  This is how "learning" is represented: numbers the director reads, not behaviour that changes.
- the six unregistered skills are registered, so `validate` exits 0 and the governance suite's
  three "baseline" failures disappear.
- OTHMODE's `project_context` projection (`reference/othmode/registries.js`) additionally passes
  through `shared_platform_capabilities` and `notes` it currently drops (served on the VPS after
  the owner's pull).

### 4.3 Execution intelligence (candidates 6, 7, 8)

- `executor.js`: at the terminal seam, for a task whose provider supervises (reports a
  `validation` verdict), record `reputation.recordOutcome(<agent>, <capability>, success)` with
  the **same capability key the router ranks by** (`capabilities_required[0] || task_type`,
  from the resolved role), `success = validation.passed === true`. Tasks without a verdict
  record nothing (unknown is not failure). An `outcome_recorded` event carries
  `reason=<capability>:<pass|fail>` to the console.
- `config/agents.json`: measured limits on `haddad-qwen` (`context_window_tokens` 8192,
  `max_output_tokens_per_turn` 1536, `locality` local, `hardware`, `unit_of_work`) and
  `locality` on the others. Informational: nothing reads them for authority.
- **Authority does not move.** Reputation only reorders candidates the registry already
  selected; the bridge allow-list floor refuses anything outside it. A test drives a reputation
  store in which `claude-code` is perfect and `haddad-qwen` is failing, and asserts the Haddad
  decision is still `haddad-agent` or DEFER — never Claude.

### 4.4 Continuation (candidate 9)

- **Rule:** after a task, the next work is (1) the authorized queue — open Issues on an intake
  label, taken in order, dependencies waited on by the bridge; then (2) a *recommendation* from
  `core/roadmap.js selectNext()` over the committed Master Vision, which the **director** may
  turn into an Issue. Nothing files work by itself; governance capabilities are never
  selectable (`isGovernanceCapability`, unchanged).
- `config/roadmap-state.json` is reconciled with `recordProgress()` — which requires
  `{ commit, tests }` — for every capability the audit proved exists; PARTIAL where only part
  exists (e.g. Adversarial Reviewer: `review_fn` has no production implementation).

### 4.5 Security (applies to all of the above)

DATA vs KNOWLEDGE vs INSTRUCTIONS vs OWNER AUTHORITY:
- repository files, OTHKM records and reuse-query output are **data**; an OTHKM record is at
  most a **claim** unless an operator promoted it; neither ever carries authority;
- **instructions** reach the executor only as a labelled GitHub Issue on an intake label, parsed
  into a closed action set; the action decides the profile, never the text;
- **owner authority** is expressed in owner messages and the handover, never in OTHKM or project
  content (the permission layer refused recording it anywhere else during V3.1, correctly).
Tests in §7 pin: reputation cannot widen the allow-list; reuse output is data-labelled and the
tool performs no write and no network; seed relationships to unknown keys and secret-shaped
content are refused; governance roadmap capabilities stay unselectable.
