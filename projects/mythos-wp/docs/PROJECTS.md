# MYTHOS WP V2.1 — Projects

A **project is a service** and the tenant of everything the panel stores: number links, contacts, conversations, messages, knowledge, rules, agent bindings, automations, notes, audit. Since V2.1 a project is created with a short form and configured from its own page; the technical fields sit under **Advanced**. Companion: `WHATSAPP_SETUP.md`, `AI_AGENTS.md`, `INTEGRATIONS.md`, `SECURITY.md`.

## 1. The list (`#/projects`)

One table: **Name · Type · Status · WhatsApp · AI**. WhatsApp shows every linked number (masked) with its connection badge; AI shows the project-level agent and its effective mode (Off / Suggest / Auto). Click a row to open the project. **New project** (admin) at the top right.

The project switcher in the header (All projects / one project) scopes the Dashboard, the Inbox, Templates, Automations and the audit filter; the project list itself always shows every project the user may see (§7).

## 2. New project (`#/projects/new`, admin)

| Field | Required | Notes |
|---|---|---|
| Project name | yes | 1–128 chars. The **slug** (`wp_projects.id`) is generated by the server: lower-cased, accents stripped, non-alphanumerics → `-`, ≤ 48 chars; `-2`, `-3`, … when the name is already taken (`Dar Hijama` → `dar-hijama`) |
| Type | yes | **Service** (any customer-facing service), **Auto** (reads the MYTHOS Auto Kitchen: parts, vehicles, prices), **Internal** (MYTHOS itself). Stored as `kind = service \| automotive \| internal` |
| Vehicle brand | — | shown for **Auto** only (`brand_car`, passed to the Kitchen) |
| Domain | — | `example.tn` shape (`^[a-z0-9.-]{3,128}$`) |
| WhatsApp | — | one of the known numbers (WhatsApp → Sync all first). Optional: more numbers can be linked later from the project page |
| AI agent | — | one existing, non-archived agent. Optional |
| Description | — | ≤ 4000 chars |
| Currency | yes | ISO 4217, default `TND` |

Conditional Auto fields: choosing **Auto** reveals *Vehicle brand* and the note "The MYTHOS Auto Kitchen (parts, vehicles, prices) is attached automatically" — the server sets `settings.kitchen = 'kitchen-mythos-auto'` for that project. Service and Internal projects own no catalogue.

**Create project** calls `POST /api/projects` (admin; module `reference/projects.js#createSimple`), one audited action that:

1. inserts the `wp_projects` row with `status = 'active'`, the generated slug, the Type, the Kitchen setting for Auto;
2. if a WhatsApp number was chosen, links it (`comms/numbers.js#link`): `dedicated` when the number is free and not personal, otherwise `shared` (with the audited `allow_personal_account` opt-in for a personal number). The new link starts with **Receiving**, **Replies** off and **AI** on inherit, exactly like a manual link (`WHATSAPP_SETUP.md` §3);
3. if an agent was chosen, binds it at project level (`ai/agents.js#link`, every number of the project).

Response: `{ project, inbox, agent, warnings[] }`. A link or bind that fails (unknown number, 409 on a dedicated neighbour, …) does **not** undo the project: the reason comes back in `warnings` and is shown as a toast; fix it from the project page. Body accepted by the API: `{ name, kind | type (service | auto | automotive | internal | other), domain?, description?, currency?, brand_car?, phone_number_id?, agent_id?, ai_mode? }`.

**Edit** (Overview → Edit, `#/projects/:id/edit`) shows the same fields without the WhatsApp / AI agent selects and saves through the generic resource (`PATCH /api/r/projects/:id`: `display_name`, `kind`, `domain`, `description`, `currency`, `brand_car`). The slug never changes.

## 3. The project page (`#/projects/:id`)

Header: name, Type · domain, status badge, **Open inbox** (switches the project selector and opens the Inbox). Tabs:

| Tab | Content |
|---|---|
| **Overview** | Name, Type, Domain, Status, Description, WhatsApp numbers (masked, connection badge), AI (agent + mode); **Edit** (admin) |
| **WhatsApp** | the numbers linked to this project: Number · Connection · **Receiving** · **Replies** · **AI** switches (admin) · Unlink; **Link a number** (a free number, linked `dedicated`). §4 |
| **AI** | Agent · Mode · Status · Save (admin) and **Test AI** (manager). §5 |
| **Catalogue** | Auto projects only: read-only search of the Kitchen (reference, title, brand, category, price, availability); a row opens the Kitchen record. §6 |
| **Members** | the users who see this project: owner / admin, `all_projects` users and the granted ones (`wp_user_projects`); Projects dialog per user (admin). `SECURITY.md` §3 |
| **Advanced** | folds: *Identity and settings* (internal id = slug, currency, vehicle brand, Kitchen key, created / updated, the `settings` JSON), *Routing rules* (with Simulate and Recent drops), *Automations* (this project), *AI agents* (the agent cards: New agent, Bind, Open), *AI runs*, *Technical integrations* (rows of this project + platform-wide), *Audit* (this project) |

Old tab links redirect: `?tab=numbers` → WhatsApp, `?tab=agents` → AI, `?tab=settings|integrations|audit` → Advanced.

## 4. Numbers of a project

Linking is done from the number side (`POST /api/whatsapp/numbers/:id/projects`, WhatsApp → **Link to project**) or from the project's WhatsApp tab (**Link a number**, always `dedicated`). Switches on each link (`PATCH /api/projects/:p/inboxes/:inbox_id`, admin, audited):

| Switch | Column | Effect |
|---|---|---|
| Receiving | `inbound_enabled` | off = dry-run: deliveries are ledgered, nothing is stored |
| Replies | `outbound_enabled` | off = no human or AI reply leaves this number |
| AI | `ai_mode` `inherit` (on) / `off` | the number-level AI switch; `suggest` / `auto` on the link are still accepted by the API and restrict the mode (§5) |

One project may own several numbers; one number may serve several projects (shared mode + routing rules — `WHATSAPP_SETUP.md` §3–5). `GET /api/projects/:p/numbers` (any) → `{ items: [{ id, phone_masked, status, receiving, inbox_id, ai_mode, account_mode, inbound_enabled, outbound_enabled }] }` (`receiving` = webhook ok **and** Receiving on).

Inbox `settings` (booleans, validated): `ai_suggest` (V1 auto-suggest switch, still honoured by `assistant.attach` when no agent is bound), `auto_reply`, `allow_personal_account` (creation-time only).

## 5. Project → AI

One card, admin to save, anyone to read:

| Field | Values | What it does |
|---|---|---|
| **Agent** | None, or any non-archived agent | the project-level binding (`wp_project_agents`, `inbox_id NULL` = every number of the project). Choosing another agent replaces the previous project-level binding; number-specific bindings made under Advanced are untouched |
| **Mode** | **Off** — the AI never answers · **Suggest** — the AI proposes, a human sends · **Auto** — the AI answers when it is sure | stored as `settings.ai_mode`; shows the *effective* mode when read |
| **Status** | Active / Disabled | computed by the server: Active when an active agent is bound and the effective mode is not Off |
| **Test AI** (manager) | a customer sentence | `POST /api/ai/agents/:id/test { project_id, text }` — a dry-run on a synthetic message: **nothing is sent, no run row**; shows Reply / Hand to human, the intent and the proposed text |

Routes (module `reference/projects.js`):

| Route | Role | Result |
|---|---|---|
| `GET /api/projects/:p/ai` | any | `{ agent: { id, name, slug, mode, engine, link_id } \| null, mode, project_mode, status: active \| disabled, agents[] }` — `mode` is the effective mode (agent × project), `project_mode` the stored `settings.ai_mode` (`inherit` when never set); `agents[]` (the choices) only for manager+ |
| `PUT /api/projects/:p/ai { agent_id?, mode? }` | admin | `agent_id` (id, or `null` to unbind) rewrites the project-level binding; `mode` ∈ `off \| suggest \| auto \| inherit` is written to `settings.ai_mode`. Audited (`setting`, `{ ai_agent, ai_mode }`). Returns the same shape as GET |

**Mode precedence — restrict only.** The mode that actually runs on a conversation is `agents.effectiveMode(agent, inbox, project)`:

1. the **agent**'s own mode (`wp_agents.mode`; a paused / archived agent = Off);
2. the **project** mode (`settings.ai_mode`, Project → AI) may lower it;
3. the **number link** (`wp_inboxes.ai_mode`, the AI switch on Project → WhatsApp or WhatsApp → number → More) may lower it again.

`off` anywhere wins; `inherit` changes nothing; `suggest` under an `auto` agent gives Suggest. No level can raise an agent above its own mode: an agent set to Suggest stays Suggest even if the project says Auto. Auto replies additionally pass every gate of `AI_AGENTS.md` §4 (confidence, Replies on, inbox open, handler AI, no open handoff, hourly cap).

Kill switch, in order of reach: Project → AI → Mode **Off** (this project), the **AI** switch on one number link (that number only), or the agent itself (Advanced → AI agents → Edit → Mode Off / Status paused: every project it serves).

## 6. Kitchen access (Auto projects)

`settings.kitchen` names a `wp_integrations` row of kind `kitchen` (default `kitchen-mythos-auto`, `http://127.0.0.1:3011`, the Kitchen Mythos Auto service `projects/ssangyong-autos`, contract 1.3.0). WP owns **no** product, price or stock data: the **Catalogue** tab and the AI tools read the Kitchen live.

| Route (any role, project access enforced) | Kitchen call |
|---|---|
| `GET /api/projects/:p/kitchen/describe` | `/api/health` + capability probe → `{ key, contract, base_host, status, read_only, database, counts, capabilities }` or `{ configured:false }` |
| `GET /api/projects/:p/kitchen/products?q=&ref=&category=&brand_car=&limit=&offset=` | `/api/products` (normalised rows, availability `IN_STOCK \| ON_ORDER \| UNAVAILABLE \| UNKNOWN`) |
| `GET /api/projects/:p/kitchen/products/:uid` | `/api/products/:uid` |
| `GET /api/projects/:p/kitchen/vehicle-models` · `…/part-categories` | `/api/vehicle-models` · `/api/part-categories` (1.2, degrades on 404) |

Failure shapes propagate as `{ ok:false, kind: UNREACHABLE | TIMEOUT | BAD_STATUS | BAD_PAYLOAD }`; the tab shows *unreachable* / *not configured* rather than guessing. A Service or Internal project has no Catalogue tab and its agents get `KITCHEN_NOT_CONFIGURED` from the kitchen tools.

## 7. Access

- owner / admin, users with `all_projects = true`, and users-file logins see every project;
- every other user sees only the projects granted in `wp_user_projects` (`bin/mythos-wp users grant|revoke`, `PATCH /api/users/:u/projects { add:[], remove:[] }` (admin), UI Settings → Users → **Projects**, or Project → Members);
- `api-util.projectFrom()` enforces it on every project-scoped route: an inaccessible project is reported as 404, exactly like an unknown one;
- `?project=all` / no project on cross-project lists (dashboard, search, contacts, agents, templates, automations) restricts to the accessible set;
- inbox-level scope still exists (`wp_inbox_members`): a user with at least one membership sees only member inboxes of that project (`GET /api/comms/my-inboxes`).

## 8. Advanced: the record and the generic resource

`wp_projects`:

| Field | Values | Notes |
|---|---|---|
| `id` | `^[a-z0-9][a-z0-9-]{1,62}$` | the slug; generated by the New project form, typed only through the generic resource or the CLI |
| `display_name`, `domain`, `brand_car`, `currency`, `description`, `notes` | | `brand_car` for Auto projects |
| `kind` | `automotive` \| `service` \| `internal` \| `other` | the form offers Service / Auto / Internal; `other` exists in the registry |
| `status` | `active` \| `planned` \| `archived` | the form creates `active`; the generic resource defaults to `planned` |
| `settings` | JSON, non-secret | `kitchen` (integration key, `null` / `false` = none), `ai_mode` (`off \| suggest \| auto \| inherit`), `timezone`, `default_agent_id`, … A key that looks like a credential is refused |
| `catalog_dsn_env`, `catalog_schema` | | **hidden legacy columns** (V1 catalogue pool): not shown by the resource, read-only, written by nothing but `seed-project`; kept for rollback only |

Generic resource `projects` (`GET/POST/PATCH/DELETE /api/r/projects`, read viewer+, write admin+, delete owner; sections *Project* / *Advanced* / *Audit*) still exists for technical edits: the `settings` JSON, `status`, `notes`, a hand-picked slug. CLI: `bin/mythos-wp seed-project <id> <display_name> <domain|-> <brand_car|-> [catalog_dsn_env|-] [catalog_schema|-]` (leave the two catalogue arguments `-`; set `settings.kitchen` instead).

Production today holds one project (`ssangyong-autos`) and one inbox. The V1 tables `wp_product_commercial` / `wp_stock` have 0 rows in production, are written by nothing, and stay only for rollback.

## 9. Onboarding a new service (summary)

1. **Projects → New project**: Name, Type (Service unless it has a parts catalogue → Auto), Domain, the number if it is already synced, the agent, Create.
2. **Members** (or Settings → Users → Projects): grant the operators; optionally inbox memberships.
3. Number: the owner creates the Evolution instance + webhook (`ops/whatsapp/evolution/customer-instance.sh`), pairs it (`qr-live.sh`), then **WhatsApp → Sync all** and **Link to project** (This project only, or Shared + routing rules under WhatsApp → Advanced).
4. On **Project → WhatsApp**: switch **Receiving** on (watch one real message land), then **Replies** (reply once).
5. **Project → AI**: Agent, Mode **Suggest**, **Test AI**; after reviewing real suggestions, **Auto**.
6. Knowledge entries (`#/r/knowledge`, `allowed_for_auto_reply`) and business rules (`#/r/rules`) as needed.

Full runbook with the pairing gotchas: `docs/MYTHOS_COMMUNICATION_OS_OPERATIONS.md` (repo level).
