## 1. The verification capability, and its real boundary

**What `tools/visual-verify.js` does, verified working this stage:**
copies the app's static surface (`index.html`, `css/`, `js/`, `assets/`,
`api.php`) into an isolated OS temp directory (never this checkout — see
its own header comment for why), serves it with `php -S 127.0.0.1:<port>`,
seeds the browser session exactly as `js/auth.js`'s `AUTH.createSession()`
does (`localStorage.mp_auth_session`), then screenshots named views with a
real headless Chromium. A hard-coded guard (`assertLoopback`) refuses any
host that is not `127.0.0.1`/`localhost` — it structurally cannot be
pointed at `uthinachess.tn`.

**Real pilot run, this stage.** Three views (`dashboard`, `nav-tache`,
`nav-inscriptions`) captured before and after a scoped candidate change —
the `--gold`/`--gold-light`/`--gold-dim` custom-property declarations in
`css/main.css` (only, in an isolated copy) changed from `#c9a84c`/`#e4c472`/
`rgba(201,168,76,.12)` to the approved `#D9A441`/`#EBCE99` (gold-200)/
`rgba(217,164,65,.12)` — the exact **MIG-1** value. Pixel diff
(`PIL.ImageChops`) against the "before" set:

| View | Changed pixels | % of frame |
|---|---|---|
| Dashboard | 443 | 0.04% |
| Mes Tâches | 6,199 | 0.54% |
| Liste d'inscription | 5,655 | 0.49% |

Every changed pixel is confined to gold-coloured chrome (buttons, borders,
active-state highlight); layout, spacing, and every non-gold colour are
byte-identical. **This proves the CSS-custom-property layer of MIG-1 is a
clean, isolated colour change with no layout regression** — genuinely new
evidence, not asserted.

**The real boundary this pilot also proved.** The CSS custom property is
not the whole story.

## 2. MIG-1 — real scope, measured directly (not the 1-value swap previously recorded)

`MYTHOS_DESIGN_DECISIONS.md`'s original MIG-1 statement — "Align Mythos
OS's implemented `--gold: #c9a84c` with the approved master `#D9A441`" —
describes a **one-value swap**. Grepping the actual application for the
literal hex, not just the CSS variable, finds **42 occurrences across 12
files**, most of them **hardcoded inside JavaScript-generated HTML strings**,
entirely outside the CSS custom-property system:

```
css/main.css                    2   (the --gold declaration + 1 SVG data-URI stroke colour)
css/professional.css             1   (--gradient-gold literal stop)
js/app.js                        2   (inline nav-btn active box-shadow, scrollbar thumb)
js/shared/accounting-bank.js    12   (modal chrome, filter inputs — inline style="" strings)
js/shared/accounting-cash.js     3   (filter inputs)
js/shared/accounting-expenses.js 1   (colour-picker default value)
js/shared/accounting-purchases.js 3  (table header/cell inline styles)
js/shared/accounting-suppliers.js 4  (search/filter inputs, category colour map ×2)
js/shared/accounting-tva.js      2   (field border-colour on validation)
js/shared/fournisseurs.js        4   (search/filter inputs, category colour map ×2)
js/shared/inscriptions.js        1   (status gradient)
js/shared/representations.js     1   (print-window inline `<style>`)
index.html                      11   (nav-btn hover/active box-shadow in a <style> block,
                                       icon-tile gradient, supplier quick-access panel ×9)
```

Reproduce with: `grep -rn "c9a84c" css/*.css js/*.js js/shared/*.js index.html`

**Why a CSS-variable-only migration would be wrong to ship.** Half the
occurrences above are in **accounting/financial UI** — bank entries,
purchases, suppliers, TVA validation — generated by JavaScript template
strings, not styled through the token system at all. Changing only
`--gold` would leave these 39 spots showing the **old** `#c9a84c` next to
UI elements now showing the **new** `#D9A441` in the same screen (e.g. the
Fournisseurs page mixes both the CSS-driven sidebar nav and a
JS-template-driven filter panel). That inconsistency is worse than doing
nothing — it is real drift, not a completed migration, and it is exactly
what this stage's pilot exists to make visible before anyone ships it.

**Execution plan, if and when authorised:**
1. Change the three CSS declarations (`css/main.css` lines 6–8) — already
   pilot-verified clean, above.
2. In the same change, update all 39 JS/HTML literal occurrences listed
   above to the same three values (`#D9A441`, `#EBCE99`, `rgba(217,164,65,…)`,
   matched to whichever role — base/light/dim — each occurrence plays).
3. Re-run `tools/visual-verify.js` with an expanded view list that visits
   the accounting/fournisseurs modules specifically (the current pilot's
   three views do not reach them — the nav requires opening those sections
   first; the tool supports adding `nav-*` IDs, but the accounting views
   are reached through in-page tabs, not top-level nav, so the view list
   needs a small extension — noted here rather than pretended solved).
4. Run the existing suites (no dedicated test file covers `css/main.css`
   or its consuming JS today — confirmed, none exists at repository root).
5. `git diff --stat` should show exactly the 12 files above, nothing else.

**Rollback:** a single `git revert` of the one migration commit — every
value above traces to one source value each, no derived state, no
migration of stored data (`appdata/`'s JSON is untouched by any of this;
these are presentation-layer literals only).

re-verified after being written, and could have been trusted for an
actual migration attempt.

## 5. What this stage does and does not authorise

**Built and verified, real and reusable:**
- `tools/visual-verify.js` — drives the real application locally, proven
  against a real scoped change, zero real data or credentials required,
  cannot target production (hard-coded guard).
- Exact, re-verified scope for MIG-1 (42 occurrences, 12 files) and MIG-2
  (93 occurrences, 14 files) — both larger than previously recorded.
- One real pixel-diff result: the MIG-1 CSS-custom-property layer alone is
  visually clean (0.04–0.54% of frame, confined to gold elements).

**Not done, and not claimed:**
- MIG-1 is **not executed** — only its CSS-property third is pilot-verified;
  the 39 JS/HTML literal sites are unmodified.
- MIG-2 and MIG-3 are **not executed** and not pilot-verified at all.
- No accounting/financial view was screenshotted (the pilot's three views
  don't reach them) — the JS-literal-heavy occurrences in MIG-1/2 are
  concentrated exactly there, so this is a real, named gap in the pilot's
  coverage, not an oversight glossed over.

  `css/forms.css`, `css/facture.css`, `css/calendrier.css`, `css/print.css`
  were copied into the pilot's isolated instance (so they rendered
  correctly) but **not individually diffed** — only the three named views
  were screenshotted, and not every stylesheet's rules are necessarily
  exercised by them.

**This is deliberately a "ready to execute," not "executed," deliverable** —
consistent with `AUTO-2`'s original reasoning for why this program does not
touch `css/main.css` without real verification, now with a real verification
