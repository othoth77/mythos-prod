### Added — MONITOR-SWAP — swap headroom is visible to the resources probe (B8, 2026-08-22)

- **The gap:** `probeResources` reported disk, memory and load but not swap, so the production VPS sat at **100% swap used (0 GB free)** with memory at 79% — under its 92% threshold — and the monitor reported `vps-resources: LIVE` with nothing to indicate the host had no paging headroom left. Found by the on-host closure audit.
- **The fix:** the probe now reports **`swap_used_pct`** and **`swap_free_gb`** alongside the existing fields, read from `/proc/meminfo` (`SwapTotal`/`SwapFree`). The collector still never shells out — the no-`child_process` contract pinned by `stc-2` §1 is unchanged.
- **Reported, not judged, by default.** Swap legitimately fills with cold pages on healthy hosts, so alarming on it out of the box would be noise. Set **`swap_warn_pct`** on the `vps-resources` probe to make exhaustion `DEGRADED`; left unset, swap is surfaced without affecting state. A configured `0` means "warn at any swap use" and is honoured as written (same discipline as the B4 threshold fix). **`probes.json` is deliberately unchanged**, so no live probe state flips as a result of this commit — verified by a real end-to-end collect: swap now visible, summary still 8 LIVE / 0 DEGRADED / 0 DOWN / 2 NOT_MONITORED.
- **Honest on hosts without swap:** `SwapTotal: 0`, an absent or unparseable `/proc/meminfo` all report both fields as `null` and never penalise the host — a missing reading is never a failed one.
- **Tests:** `stc-2` **77/0** (+11 assertions: reported values, exhaustion visible without a state change, threshold opt-in, zero honoured, no-swap hosts, unreadable meminfo). Relevant battery **393/0**. OTH-KNOWLEDGE live gate re-run **LIVE PASS, exit 0** — untouched.

### Fixed — GATE-RELIABILITY — three documented production gates could not be trusted (2026-08-22)

Found by the on-host closure audit of 2026-08-22 and fixed here. All three were verified against the production VPS, not only in tests.

- **A dead API reported LIVE (B2).** `ssangyong.autos` serves a catch-all/SPA fallback: **every** unmatched path answers HTTP 200 with the storefront `index.html` — `/api/health` and `/zzz-nonexistent` alike. The `sya-api` probe asserts only `expect_status: [200]`, so enabling it would have certified a catalog API that has been down since 2026-08-16 as healthy. `probeHttps` now supports **`expect_content_type`**, checked before the body assertion and reported with the media type actually received; the shipped `sya-api` probe carries `expect_content_type: "application/json"` and a note that it must stay. Verified against the live host: status-only → `LIVE` (the defect), with content-type → `DOWN`. The probe **remains `enabled: false`** — confirming the real health path is still operator work (SYA-API-1) — but it can no longer false-green when switched on. Probes without `expect_content_type` are unaffected.
- **The drift audit invented drift (B3).** `scripts/production-sync-audit.sh` tested each expected timer with `systemctl list-timers … | grep -q "$t"`. `grep -q` exits at the first match, SIGPIPEs `systemctl` mid-write, and a following invocation returns truncated output — so installed timers were reported missing in roughly a quarter of runs, naming a different timer each time (**11 false findings in 48 checks** on the production host). Section 5 now queries each unit directly with `systemctl is-enabled` / `is-active`, which is per-unit and deterministic: **0 false findings in 48 checks**. It also newly distinguishes *installed but not active* from *not installed* — a state the old check passed silently.
- **A 73%-full disk reported LIVE against a 0% threshold (B4).** The monitor defaulted thresholds with `x || dflt`, and `0` is falsy — so a configured `disk_warn_pct: 0` was silently rewritten to `85`. A `num(v, dflt)` helper now applies the default only when the value is genuinely absent, across all seven thresholds (`disk_warn_pct`, `disk_down_pct`, `mem_warn_pct`, `fresh_hours`, `degraded_hours`, `cert_down_days`, `cert_warn_days`), each of which has a meaningful `0`. This restored `tests/stc-2-monitor-test.js` to green — it had been failing **53/1** on the production host, so the previously recorded "stc-2 54/0" did not hold there. Shipped thresholds are 85/95/92, so live alerting was never affected in practice.
- **Tests:** stc-2 **66/0** (was 54 assertions; +12 covering zero-thresholds, the SPA-fallback guard, and the shipped `sya-api` guard) · production-sync-audit **24/0** (+4 pinning deterministic timer detection). Full non-root battery **716/0**; OTH-KNOWLEDGE live gate re-run **LIVE PASS, exit 0** — unchanged.
